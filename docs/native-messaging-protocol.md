# Native Messaging Protocol — Extension ↔ Helper

This is the wire contract between `extension/` and `helper/`. Both sides
must implement exactly this — it's the seam between two independently
built packages, so treat it as an API contract, not a suggestion.

Transport: [Chrome Native Messaging](https://developer.chrome.com/docs/apps/nativeMessaging)
over stdio. Each message is a JSON object, framed per Chrome's spec
(4-byte little-endian length prefix + UTF-8 JSON on the native host side;
the extension side's `chrome.runtime.connectNative`/`postMessage` handles
framing automatically).

- Host name: `com.ainotetaker.helper`
- Extension ID (fixed, from the committed `manifest.json` `key` field):
  `jidooookkdbbbhkkdmcajnnnhhphodok`
- The helper's native messaging host manifest must allowlist exactly this
  extension ID (`chrome-extension://jidooookkdbbbhkkdmcajnnnhhphodok/`).
- Current wire protocol version: `2`. The helper advertises its version after
  every successful `hello`; the extension must stop recording and show an
  update path when the version is unsupported.

## Process model: two binaries, not one

Chrome spawns a **fresh process per `connectNative()` call** and kills it
when the port disconnects — a Native Messaging host is not meant to be a
long-lived background process. That's in tension with the architecture's
"the helper is a persistent process that owns the pipeline" requirement
(§3.1 of the spec), so `helper/` ships two binaries instead of one:

- **`notetaker-nm-host`** — the tiny binary actually registered in the host
  manifest as `path`. Chrome spawns/kills this per connection. It
  understands nothing about message schemas; it just relays raw
  length-prefixed frames between its stdio (talking to Chrome) and a local
  IPC socket (talking to the real app). This keeps it trivial and
  crash-irrelevant — losing it loses nothing, since it holds no state.
- **`notetaker-helper`** — the persistent tray app: owns audio capture, the
  pipeline, and crash-recovery state, independent of whether the extension
  is currently connected. It listens on a local Unix domain socket /
  Windows named pipe (deliberately not a TCP/loopback port — same
  reasoning as the Native-Messaging-over-open-port rejection elsewhere in
  this doc: no reason to expose anything reachable by other local
  processes or, worse, a browser tab's JS).

The message shapes above are relayed unchanged by this process split. See
`helper/crates/app/src/ipc.rs` for the implementation.

## Pairing token (defense in depth)

Native Messaging already restricts the channel to this extension ID at the
OS level, but we add one more layer: on first connection ever, the helper
generates a random pairing token and sends it to the extension in a
`paired` message. The extension stores it in `chrome.storage.local` and
presents it in the first `hello` frame of every subsequent connection. The
helper rejects a connection whose first frame is not `hello`, and rejects the
connection when that token is missing or mismatched. All later frames inherit
that connection-level authentication; the token is intentionally not copied
into each settings/audio-control message. The token is stored in a mode-0600
file on Unix-like systems.

## Messages: extension → helper

```jsonc
// First message on every connection.
{ "type": "hello", "pairingToken": "<stored token, or null on first ever connect>" }

// Push current settings down (on connect, and whenever settings change).
// Provider keys live here — the helper does not persist them to its own
// disk; they're held in memory for the life of the process and re-sent
// each time the extension connects.
{
  "type": "settings",
  "transcriptionProvider": "deepgram" | "groq",
  "summarizationProvider": "claude" | "gemini" | "deepseek",
  "apiKeys": { "deepgram": "...", "claude": "...", "groq": "...", "gemini": "...", "deepseek": "..." },
  "webapp": { "url": "https://...", "token": "..." }, // optional, null if not configured
  "defaultMeetingMode": "general" | "standup" | "sales" | "one_on_one" | "interview" | "custom",
  "customVocabulary": ["product name", "customer acronym"],
  "customSummaryInstructions": "Optional additional summary guidance."
}

{ "type": "start_recording", "meetingId": "<uuid, generated by extension>", "meetingMode": "general", "captureSource": "desktop" | "meet" }
{ "type": "stop_recording", "meetingId": "<uuid>" }

// Google Meet browser capture only. `captureSource: "meet"` starts the
// helper pipeline without opening an OS capture device. The offscreen
// document sends independent mic and remote-audio PCM16 chunks. Each decoded
// chunk must be non-empty, even-length PCM16, 48,000 Hz, and <= 64 KiB.
{
  "type": "audio_chunk",
  "meetingId": "<uuid>",
  "channel": "mic" | "speaker",
  "sampleRateHz": 48000,
  "pcm16Base64": "<base64 PCM16 bytes>"
}

// Device setup checks for desktop/helper capture.
{ "type": "audio_preflight" }
{ "type": "audio_probe" }

// In response to a "recovered_recording" message from the helper (see below).
{ "type": "resume_recording", "meetingId": "<uuid>" }
{ "type": "discard_recording", "meetingId": "<uuid>" }
{ "type": "delete_meeting", "meetingId": "<uuid>" }

// Settings-page "test key" button. The extension never calls provider APIs
// directly (see extension/CLAUDE.md) — this is why "test key" exists as a
// protocol message instead of a `fetch()` call from the settings page.
{ "type": "test_provider_key", "provider": "deepgram" | "groq" | "claude" | "gemini" | "deepseek", "key": "..." }
```

## Messages: helper → extension

```jsonc
{ "type": "paired", "pairingToken": "<new token>" } // only on first-ever connection

// Sent after every authenticated hello, including reconnects.
{
  "type": "helper_info",
  "helperVersion": "0.1.0",
  "protocolVersion": 2,
  "platform": "linux | macos | windows"
}

{ "type": "recording_started", "meetingId": "<uuid>" }
{ "type": "recording_stopped", "meetingId": "<uuid>" }

// When a Native Messaging connection is recreated while the persistent
// helper is still recording, the helper replays recording_started and routes
// subsequent meeting events to the new connection. This makes MV3 worker
// suspension transparent to the capture pipeline.

// Streamed continuously while recording.
{
  "type": "transcript_partial",
  "meetingId": "<uuid>",
  "speaker": "you" | "them" | "them-2" | ...,
  "text": "...",
  "isFinal": false,
  "utteranceId": 0
}
// utteranceId increments per channel each time a final segment is
// emitted; the extension uses (speaker, utteranceId) to know whether an
// incoming message replaces the currently-shown in-progress line or
// starts a new one.

// Once the LLM summarization call returns, after stop_recording.
{
  "type": "summary_ready",
  "meetingId": "<uuid>",
  "summary": "...",
  "actionItems": [{ "text": "...", "owner": "..." }]
}

// On any pipeline failure (network, rate limit, bad key). The raw audio is
// already safe on disk per the resilience guarantee — this just tells the
// UI what happened.
{ "type": "error", "meetingId": "<uuid> | null", "code": "string", "message": "human-readable" }

// On helper startup, if an unclean-shutdown recording was found on disk.
{ "type": "recovered_recording", "meetingId": "<uuid>", "startedAt": "<ISO 8601>" }

// Reply to "test_provider_key". Correlate by "provider" — the settings page
// only ever has one test in flight per provider at a time.
{ "type": "provider_key_test_result", "provider": "deepgram" | "groq" | "claude" | "gemini" | "deepseek", "valid": true, "message": "human-readable" }

// Returned by audio_preflight. `ready` is a prerequisite, not proof of a
// real meeting.
{
  "type": "audio_status",
  "platform": "linux | macos | windows",
  "driver": "BlackHole | VB-CABLE | AI Notetaker | ...",
  "driverInstalled": true,
  "microphone": "device name or null",
  "speaker": "device name or null",
  "ready": true,
  "guidance": "human-readable setup guidance"
}

// Returned by audio_probe after a short local capture window.
{ "type": "audio_probe_result", "micFrames": 123, "speakerFrames": 456, "passed": true, "message": "human-readable" }
```

## Error codes (non-exhaustive, extend as needed)

- `provider_auth_failed` — API key rejected by the provider
- `provider_rate_limited` — retry is already queued; informational only
- `provider_unreachable` — network failure; retry is already queued
- `device_not_found` — the virtual audio device isn't selected/available
- `helper_not_paired` — pairing token missing/invalid (shouldn't normally
  surface to a user; indicates a bug if it does)
